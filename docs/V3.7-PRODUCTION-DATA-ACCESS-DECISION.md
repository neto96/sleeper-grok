# V3.7 — Production quality data access decision

Research date: 2026-11-11 (UTC). Starting commit: `aa5f839fae5760be75b029eb902f8b98eef97349`.

## Decision

Pursue a separately authorized FantasyPros HOF production API key for an authenticated, user-only application. First obtain written confirmation that this hosted fantasy analyzer and its proposed derived scores/exports fit the license. Then validate an actual ROS response and its coverage privately. Documentation establishes a technical route, not an entitlement or permission for this particular app. Phase 3 remains unimplemented and unapproved for production.

The current blockers are retained evidence coverage (9/150 rostered players, 4/580 free agents, 0/12 complete rosters) and unvalidated production access. These are aggregate findings from the previous local study, not current provider-wide coverage measurements. The public synthetic fixtures cannot reconstruct that census. A bulk API response might improve coverage substantially; it cannot guarantee that every fringe player is ranked.

## Minimum evidence

The first possible quality feature should require only rankings and identity metadata. FantasyPros projections are **not required**: the existing projected-lineup layer remains independent. Selecting that feature or a quality curve is outside this task.

| Field | Need | Proposed handling |
| --- | --- | --- |
| FantasyPros player ID and resolved Sleeper ID | Required | Stable crosswalk with match method, evidence and review state |
| Overall ROS ECR | Required for cross-position quality comparisons | Nullable; absence never becomes zero or a positional substitute |
| Positional ROS ECR | Optional for an overall-only asset view; useful for positional context and coverage diagnostics | Separate pool and timestamp; never fill an overall-rank gap with this value |
| Provider, sport, season, scoring, ranking type, pool | Required | FantasyPros / NFL / requested season / PPR / ROS / ALL or named position; explicitly restrict design to redraft 1QB |
| Provider update timestamp | Required to claim source freshness | Validate timezone/units; missing timestamp means freshness unknown, not current |
| Retrieval timestamp | Required | Generated by our server; does not reset age of unchanged source data |
| Position | Required | Offensive eligibility and matching validation |
| Player name | Required for readable review and unresolved matches | Minimal name only |
| Team | Useful for identity fallback | Nullable, time-sensitive; never identity by itself |
| Capture counts and validation state | Required at pool level | Returned count, mapped/unmapped counts, completeness/truncation checks, source and schema version |

Do not retain images, news, biographies, ownership percentages, expert profiles, full league rosters or unused projections in this reference cache. Injury, bye and current usability continue to come through existing availability logic, separate from ROS asset quality. Quality indices are neither fantasy points nor trade prices.

## API endpoint plan

Official base: `https://api.fantasypros.com/public/v2/json`; authentication uses the `x-api-key` header. The routes below are documented candidates, **not authenticated requests executed in this investigation**. [1][2]

| Purpose | Candidate GET request (relative to base) | Minimum response fields to validate |
| --- | --- | --- |
| Identity bootstrap | `/nfl/players?external_ids=yahoo:espn` | `players`, `player_id`, `player_name`, `position_id`, `team_id`; requested external IDs, validating actual key names |
| Overall PPR ROS | `/nfl/2026/consensus-rankings?position=ALL&scoring=PPR&type=ROS` | `year`, `scoring`, `position_id`, `ranking_type_name`, `count`, `last_updated_ts`, `players`; row `player_id`, `rank_ecr` |
| Position-specific ROS | Same rankings route with `position=QB`, `RB`, `WR`, or `TE` | Same fields; store each response as its own pool |
| Optional future ROS projections | `/nfl/2026/projections?position=RB&ros=true` (repeat positions only if later justified) | `season`, `week`, `count`, `positions`, `scoring`, `players`; row `fpid`, `position_id`, `team_id`, `stats` |

The current public OpenAPI document explicitly defines `type=ROS`, `scoring=PPR`, and these positions. It also exposes ranking-row `pos_rank` and `player_yahoo_id`, and metadata `sportsdata_player_id` described as a Sportradar ID. Sleeper is not a documented `external_ids` option. Metadata has `update=YYYY-MM-DD`; no pagination parameter appears on these two collection routes. [2]

Implementation validation still needed: confirm pool identity, rank types, timestamp units, season handling and absence of hidden result caps on the production entitlement. Omit `week` initially for ROS; confirm its effect rather than assuming the current week or week zero selects ROS. Do not use metadata's generic ECR fields as ROS without explicit pool provenance. A positional label returned inside ALL stays contextual to that response until its semantics are verified; it is not silently equated with an independently queried positional pool.

The projection route documents `ros=true`, but its listed request parameters do not establish a PPR scoring selector despite a response scoring field. Do not assume defaults match this league. Previously empty ROS projection calls remain unresolved; neither a documented route nor an example proves nonempty production data. No projection acquisition is needed for this proposal.

The schema describes itself as a free limited API while the product page directs premium users to the same reference. Confirm production response depth and entitlement rather than treating the schema's “Production” server label as license approval. [1][2]

## Coverage acquisition and request budget

Proposed acquisition, subject to permission and validation:

1. Obtain one metadata collection for identity mapping. Do not restrict it to `ecr=included`: unranked rostered players still need an identity. Retain only relevant minimal fields.
2. Obtain one complete ALL/PPR/ROS response, then join locally to current Sleeper roster IDs and free-agent IDs. No league/user identifiers need to be sent to FantasyPros.
3. When positional context is required, acquire four separate QB/RB/WR/TE pools. Filter to offense locally without renumbering overall ranks. Excluding K/DST does not redefine ALL.
4. Resolve each rostered offensive player and each candidate's status: current, stale, missing, identity_unresolved or unsupported. Distinguish absent from returned pool, known but unranked, response failure and unresolved identity. Keep overall coverage separate from positional coverage.
5. Atomically accept validated pools; an empty, wrong-season, malformed or unexpectedly truncated response must not replace a good capture. Compare returned row count to `count`, unique IDs, prior capture size and expected ranked IDs. A matching count alone does not prove complete provider coverage.

| Capture scope | Requests, assuming documented unpaginated collections |
| --- | ---: |
| Minimum initial capture: metadata + ALL | 2 |
| Minimum ranking-only refresh | 1 |
| Full five-pool initial capture: metadata + ALL/QB/RB/WR/TE | 6 |
| Full five-pool ranking refresh | 5 |
| Four scheduled ranking captures/day plus daily metadata | 5 minimum; 21 with five pools |

These are estimates, not measured production quotas. “Bulk” here means ordinary collection responses; it does not assume entitlement to the separately advertised commercial bulk/history product. If the personal key truncates these collections, request clarification rather than multiplying single-player calls or bypassing limits.

All 150 rostered players and all 580 captured free agents are coverage denominators to inspect, not a promise of 730 ranked players. For a future waiver asset view, show only supported ranked candidates with an explicit coverage label and retain immediate-help recommendations separately. Do not claim “best overall free agent” if relevant candidates lack evidence. Lineup/replacement migration requires complete evidence for every eligible candidate and replacement in each compared roster, not merely its current starters. Re-run the shadow study on permitted captures before proposing migration.

## Deterministic identity resolution

Use an auditable FantasyPros ID → Sleeper ID table, never a guessed numeric equivalence.

1. Reuse an explicitly verified mapping keyed by provider ID, retaining provenance and any conflicts.
2. Bootstrap new entries using unique shared Yahoo or ESPN IDs where both feeds supply them. Sleeper documents those external ID fields; they may be null. Exact unique Sportradar UUID matching is another possible bridge, after verifying field semantics. Do not confuse it with a numeric FantasyData ID. [2][6]
3. If no stable bridge exists, require a unique normalized full name + compatible position + normalized current team. Normalize case, Unicode, spacing and punctuation deterministically; use reviewed aliases for suffix/name changes. Team changes or missing team information block automatic fallback matching rather than encouraging fuzzy guesses.
4. Reject multiple matches, conflicting external IDs, incompatible positions, or duplicate provider-to-Sleeper mappings. Mark identity_unresolved and require a reviewed mapping override. An established ID match can survive a team change, but record the metadata discrepancy.

Check both directions for uniqueness. Keep a small versioned mapping table separate from mutable rankings and record how each entry was resolved. Validate actual external-ID response key names before binding an adapter. No direct Sleeper ID field is established by the inspected FantasyPros schema.

## Refresh, storage and failure policy

**Provider evidence:** the linked 2020 terms encourage caching, specify confidential keys, state 1 request/second and 100/day, and contain attribution and non-compete restrictions. Their termination provisions allow only conditional continued personal use. Current premium guidance promises higher limits without publishing exact numbers. No current premium-specific cache TTL or retention period was established. Confirm which terms and quotas govern the issued key. [3][4]

**Proposed engineering policy — not provider-required TTLs:**

- Refresh rankings every six hours during the season, sharing one capture across rosters and requests. Refresh metadata daily; incremental metadata updates can be considered only after bootstrap semantics are verified.
- Treat evidence as current only when retrieval age is at most 24 hours and verified source-update age is at most 72 hours. Unknown/future timestamps fail the freshness gate. The 72-hour threshold is a conservative starting experiment, not a provider promise; repeated captures must show whether it is appropriate.
- A page load reads the cache, never calls the provider. Authorized manual refresh uses a shared lock, a minimum one-hour cooldown, and the same rate budget; repeated clicks cannot force calls.
- Serialize calls at no more than one per second and cap proposed total usage at 50/day until account quotas are confirmed. The five-pool schedule costs 21/day before retries. Apply `Retry-After` when supplied, bounded backoff for transient failures, at most one retry per failed call, and a global budget that includes retries/manual refreshes. Stop on authentication/entitlement failures pending operator resolution.
- On outage, retain the last validated capture within permitted retention, but do not mark it fresh on retry. Once stale, withhold quality-aware comparisons and use the unchanged Sleeper projection/structural path. Do not replace missing evidence with zero or stale indices.
- Store minimal normalized records in private persistent server storage, never in Git, static assets, public cache URLs, client credentials, snapshot JSON or raw response logs. Authenticate the viewer and every data endpoint before exposing any permitted derived display. Do not rely on an obscure URL or frontend-only hiding.
- Propose one active capture plus one previous validated capture, maximum seven-day retention, only if the provider permits it; otherwise follow its stricter limit. Log counts/status/errors rather than provider bodies. Backups and deletion jobs must honor the same approved policy. A public endpoint that returns a whole cache would defeat server-only storage.
- On license expiry/revocation, stop fetching and disable quality presentation until allowed use/retention is clarified; delete according to the governing agreement. No assumed perpetual archive rights.

These policies are design choices only. No scheduler, database table, runtime adapter or credential was added.

## Subscription and user action

Current API pricing advertises HOF personal production access **from $8.99/month with annual billing** (arithmetic equivalent $107.88/year before any taxes or checkout adjustments). This is a starting advertised rate, not a verified checkout quote or monthly-billing offer. No incremental personal API fee is advertised for an eligible HOF member. [1]

An active **paid** HOF subscription is required; a free trial does not qualify. The account owner requests/activates access at [the API-key request page](https://secure.fantasypros.com/api-keys/request/), which redirects to account sign-in. Keep membership active. [3][7]

Recommended sequence:

1. Send the support questions below with the intended user-only hosting mode. Resolve non-compete, display, derived-score and export permission **before purchasing solely for this project**.
2. If confirmed, purchase/retain paid HOF and request a personal production key through the account portal. If support instead requires a commercial agreement, obtain its scope and quote before deciding.
3. Keep any future key in the hosting platform's server-side secret manager; never paste it into this repository, a public Grok prompt, or chat. No key is requested or installed in this task.
4. In a separately authorized follow-up, privately test the documented collection routes, record only sanitized coverage/error metrics, validate identity and freshness, and rerun shadow comparisons. A successful HTTP response alone does not open Phase 3.

A separate commercial agreement is not established as necessary for strictly personal use, but the analyzer's overlap with FantasyPros tools creates a specific unresolved question. Public redistribution cannot be assumed permitted merely because the app is free. [3][4]
